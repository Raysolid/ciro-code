title: 规划一次改动
description: 用 Plan 模式产出分步方案与测试清单，审阅后再动手改码。
---

多文件重构、公共 API 变更或复杂逻辑升级时，直接改码容易漏边。**Plan 模式**只读搜索并产出计划卡片，禁止改源文件——先定方案再落地。

---

## 何时用 Plan

- 涉及 3 个以上文件的交互式重构；
- 改公共契约（API Schema、表结构、核心状态机）；
- 需要先对齐方案再开工的较大功能。

:::tip[小改动可跳过]
单文件小修或目标已明确的函数实现，可直接走 [实现并验证](/workflows/implement-and-verify/)（Agent 模式）。
:::

---

## 规划步骤

### 1. 切换到 Plan
顶栏点 **Plan**，或在 Composer 输入：

```text
/mode plan
```

### 2. 下达带约束的规划指令

```text
我们需要把现有 Axios 请求层重构为原生 fetch 与 apiClient 单例。

约束：
1. 保持现有 API 函数签名与返回类型兼容；
2. 统一处理 401 登出与全局错误 Toast；
3. 给出分步实施计划与单测验收方式。

注意：此刻只出方案，不要修改任何源文件。
```

### 3. 人工审查计划
核对结构化计划：
- [ ] 步骤是否够细，单步能否独立编译/测试？
- [ ] 是否覆盖边界异常与相关测试？
- [ ] 是否符合当前技术选型？

不妥就继续对话调整（例如：「第 2 步先保留 Axios 别名过渡」），直到方案可接受。

### 4. 切到 Agent 执行
顶栏切到 **Agent**，再发开工指令：

```text
方案已通过。请严格按上述计划的第 1、2 步实施，并自动运行 npm test 验证。
```

---

## 常见误区

- ❌ **方案未定就切 Agent**：容易失去整体节奏、过早改乱代码；
- ❌ **计划里没有验收方式**：好计划应写明如何证明成功（单测命令或断言）。
